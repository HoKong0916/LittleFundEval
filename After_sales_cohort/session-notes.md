# 售后队列分析 — 会话纪要

> 时间：2026-11-11 ｜ 配套报告：`refund-demo.html` ｜ 数据：`assets/` 下两个 CSV
> 说明：本文件是本次会话的结构化纪要——保留原始问题、口径推导与核心结论，便于回顾与向领导汇报，非逐字聊天记录。

---

## 1. 需求背景

领导原话：

> 不同周期退款的分析；比如支付后7天、30天内的取消订单率；发货后7天、30天内的售后退款率、补发率。

背景补充（客服KPI口径）：退款率 = **当月处理退款金额 ÷ 上月发货金额**。

---

## 2. 三个困惑的解答

### 困惑一：客服KPI 与"发货后30天售后退款率"是不是大同小异？

不是。本质区别在于**分子分母是否同源**：

| | 客服KPI（期间比） | 队列口径（批次比） |
|---|---|---|
| 分子 | 当月处理的退款——混着历史多月发货批次的订单 | 同一批订单产生的退款 |
| 分母 | 上月发货金额——单一批次 | 同一批订单的发货金额 |
| 分子分母 | **不同源** | **同源** |
| 能做什么 | 只能看总体水位 | 可拆解 / 归因 / 比趋势 / 预警 |

客服KPI是"财务期间"视角（钱在当月进出），队列口径是"订单批次"视角（这一批货卖得怎么样）。

### 困惑二：某月发货金额缩水 → 本月退款率激增，是不是很无厘头？

不是无厘头，是**口径的结构性缺陷**（分母效应）。KPI的变动可以拆成三部分：

**KPI变动 = 发货规模效应（分母）× 批次结构（大促批次的退款来得更晚更多）× 处理时效**

模拟数据里的实证：黑五（2025-11）发货放大1.7倍 → 2025-12 KPI 3.56% 显得虚低、2026-01 跳到 5.18% 虚高（跳升25.85%纯粹是分母效应），而同期的队列外推终率基本走平——**队列口径不为分母波动所动**。

### 困惑三：已知退款约54%落在发货后30天内、取消约90%落在头7天内，能干嘛？

这两条就是**实现曲线**，是整个方法论的地基：

- 退款30天只实现约54% → **终率 ≈ 30天率 ÷ R30**（模拟实测 R30 = 59%，与真实54%同量级）
- 取消7天已实现约92% → 7天读数 ≈ 终值，几乎不用外推
- **实现速度分品类差异巨大**（模拟：3C电子30天实现仅44.5% vs 服饰89.8%）→ 外推必须用分品类R值，否则3C终率会被严重低估
- 未成熟队列的表面率会"骗人"：模拟中2026-10队列表面30天退款率骤降到2.98%，但窗口只覆盖36%，外推终率6.61%实际走平偏升——**不外推就会把"还没发生"误读成"变好了"**

## 3. 队列指标表是什么

**一行 = 同月支付（取消）或同月发货（退款/补发）的同一批订单；一列 = 一个窗口指标。**

| 队列月份 | 7天率 | 30天率 | 窗口覆盖度 | 外推终率 | 成熟度 |
|---|---|---|---|---|---|
| 2026-05 | … | … | 100% | 5.67% | 已成熟 |
| 2026-09 | … | … | 高 | 7.10% | 接近成熟 |
| 2026-10 | … | 2.98%↓ | 36% | 6.61%↑ | 进行中（表面在骗人） |

四个关键设计：

1. **锚点**：取消锚**支付日**（取消的单没发过货）；退款/补发锚**发货日**（必然发过货）。用户口中的"取消90%在发货后7天内"实际是**支付后7天内**——锚点必须修正，否则取消订单根本没发货日可锚。
2. **时间口径**：用**申请时间**而非处理完成时间（处理时间受客服排班/流程影响，会污染"用户为什么退"的信号）。
3. **无偏窗口计算**：未成熟队列的分母只计入"窗口已关闭"的订单（比如算7天率时，只统计发货已满7天的订单），表面率（全分母）作对照列展示偏差。
4. **右删失**：申请日大于"今天"的事件不会发生——真实业务里"退款还没来得及发生"，模拟必须复刻这一点，否则进行中月份的率会永久虚低。

## 4. 时间窗 ↔ 责任环节映射（洞察的主轴）

| 时间窗 | 责任环节 | 典型原因 |
|---|---|---|
| 支付后 0-7 天取消 | 决策 / 备货 | 下单冲动、比价、重复下单 |
| 支付后 7-30 天取消 | **履约时效** | "等太久"还没发货 |
| 发货后 0-7 天退款 | **物流型** | 货还没到就退：丢件、破损、物流停滞、拦截 |
| 发货后 7-30 天退款 | **商品型** | 质量、尺码、描述不符、欧盟14天无理由 |
| 发货后 30 天以上 | 潜在缺陷 / 拒付 | 潜在故障集中爆发、chargeback（最长120天） |

同一个"退款率"，落在不同窗口就是不同部门的责任——这正是领导那句需求的价值：**窗口不是细节，是归因的坐标系**。

---

## 5. KPI 拆解桥（与客服KPI的和解）

KPI不是没用，而是要拆开读：

**KPI变动 = 发货规模效应（分母）× 批次结构 × 处理时效**

- 2026-08起KPI持续上行，同期队列外推终率同步走高 → **有队列背书，是真恶化**，要介入
- 黑五前后KPI剧烈波动（12月虚低/1月虚高），队列终率走平 → **分母假象**，不用慌
- 拆解桥的作用：让"这月KPI涨了"变成"涨的多少来自分母、多少来自真实质量"

## 6. 模拟数据设定（demo报告的数据来源）

- **规模**：14个月（2025-09 ~ 2026-11），每月基数8000单，黑五×1.7，共约11.7万订单、8,840条售后事件
- **维度**：4站点（US/DE/UK/AU）× 4供应商（S1-S4，S4自2026-03上新）× 24个SKU × 4品类（3C电子/服饰/家居/美妆）
- **右删失基准日**：2026-11-10
- **植入的5条故事线**（用来演示方法论的探测能力）：
  1. **S2供应商-3C品类质量恶化**：随月份线性上升，终率8.93% vs 基线4.5%，每月多损$1.38万
  2. **US站点2026-08物流商切换**：发货后0-7天物流型退款 0.30% → 1.03%
  3. **DE含欧盟14天无理由**：剔除该原因后DE终率2.66% < US 2.79%，排名反转
  4. **发货SLA与取消率正相关**：SLA≤2天时取消率最低，全站拉齐可月省$3,621
  5. **退款高度集中**：Top10 SKU（24分之一）占退款金额约80%
- 报告内全部数字由同一套模拟数据动态计算（R30=59.21%对齐真实54%量级）

## 7. 落地工作计划（把领导需求翻译成可执行5步）

1. **定锚点、备两张底表**：订单表（支付日、发货日、金额、站点、供应商、商品）+ 售后事件表（事件类型、申请日、原因、金额）
2. **建队列指标表**：按月分批，算各窗口率 + 窗口覆盖度 + 外推终率 + 成熟度标签
3. **画实现曲线、定分品类R值**：用历史成熟队列标定 R7/R30，之后每月自动外推
4. **KPI拆解桥**：每月把客服KPI的变化拆成规模效应 / 批次结构 / 真实质量三块
5. **归因与行动**：窗口×站点/供应商/商品交叉下钻、帕累托聚焦Top SKU、SLA与履约时效联动

## 8. 数据字典（assets/ 下两个 CSV）

**orders.csv**（约11.7万行，一行一张订单）

| 字段 | 含义 |
|---|---|
| order_id | 订单号 |
| pay_date | 支付日期（取消队列的锚点） |
| site | 站点：US / DE / UK / AU |
| supplier | 供应商：S1-S4 |
| category | 品类：3C电子 / 服饰 / 家居 / 美妆 |
| product | SKU编号 |
| amount_usd | 订单金额（美元） |
| cancelled | 是否取消：0/1 |
| cancel_offset_d | 取消距支付天数 |
| shipped | 是否发货：0/1 |
| ship_date | 发货日期（退款/补发队列的锚点；取消单为空） |

**after_sales_events.csv**（约8,800行，一行一个售后事件）

| 字段 | 含义 |
|---|---|
| order_id | 关联订单号 |
| event_type | 事件类型：取消 / 退款 / 补发 |
| apply_date | 申请日期（口径用申请时间，非处理时间） |
| offset_from_anchor_d | 距锚点天数：取消=距支付日，退款/补发=距发货日 |
| reason | 售后原因（用户取消、质量缺陷/无法使用、物流停滞、丢件、尺码不符等） |
| amount_usd | 事件金额（美元） |

> CSV 为 UTF-8 带 BOM 编码，Excel 双击直接打开；pandas 读取用 `encoding='utf-8-sig'`。
